// why I built this

The best interview answers were already in my projects. I just couldn't find them when I needed them.

When I started interviewing for junior developer roles, I kept running into the same problem. Interviewers asked things like "Tell me about a technical challenge you faced" or "Why did you build it that way?" I'd done the work, but the details were scattered across commits, half-remembered bugs and old notes.

So I built the tool I wanted: one place to write my stories in STAR format and practise them out loud, and a journal to capture why I made each decision on my projects, what broke, and where AI helped, right next to the commits where it happened.

I like building things that make people's lives a little easier. This one started by making mine easier.

// what it does

Two halves that feed each other

S·T·A·R

Story bank

Write behavioural answers as Situation, Task, Action and Result, with a brainstorm space beside them. Tag stories by theme and see which themes you haven't covered.

0:42

Practice mode

Timed questions, voice recording with playback, and live transcription. Rate each answer and spaced repetition brings back the shaky ones sooner.

a1b2c3d

Project journal

Log decisions, issues and fixes, AI usage and lessons learned, linked to commits imported from GitHub. Filter them and export them as Markdown.

→ Q

From commits to answers

Turn a note into a STAR draft in one click, or generate the questions an interviewer would ask about a project and practise them.

Q1.

Question library

Paste questions from job postings or right after an interview. Workbench cleans them up, sorts them by type, and tracks which companies asked what.

▦

Contributions graph

A GitHub-style year of activity across commits, notes, practice and stories, with streaks, so you can see the habit build.

// how it's built

A small, real Django app

$ workbench --stack

backend Django 5 · Python

database PostgreSQL on Supabase

hosting Vercel (serverless functions + cron)

frontend Server-rendered templates, vanilla JS and CSS

tests Django test suite, run on every change

  • Per-user data. Every query is scoped to the signed-in account, which is what lets a public demo sit safely beside private data.
  • Commit import. Reads a local repo with git log, or pulls from the GitHub API when hosted.
  • Spaced repetition. A simplified SM-2 algorithm decides when each question comes back.
  • Nightly reset. A Vercel cron job re-seeds the demo with fresh sample data.
  • No framework front end. IDE-style tabs, the activity graph and practice timer are plain JavaScript.
